    System status

    Read-only. Database reads come from /d1-usage: rows read today as recorded by the Worker, against the daily limit the same response reports. It is a lower bound (requests reading fewer than 50 rows are not recorded) and the counter resets at 00:00 UTC. WARNING uses the backend alert's own thresholds (above 60% used, or above 85% on a reliable projection); CRITICAL means the limit is reached; STALE means no measurement in the last 2 hours. The projection is reliable when the whole day so far was measured, and provisional when recording covered only part of it (it is then the measured hourly rate over 24 hours, shown but not used for the status). Alerts shows the backend's alert state: an active alert is one open GitHub issue labelled ops-alert, opened once, updated in place and closed on recovery; with none open, PASSING also needs a recent successful run of the checks (stale predictions, stopped workflows, daily read limit). Notifications are GitHub's own, for the issue and for failed runs. Scheduled predictions come from /prediction-freshness (all 12 logged series: 3 assets × 2 horizons × core and challenger). Event detection comes from /api/events/health. The funding collector line is the public run history of its GitHub Actions workflow. A green status needs an explicit healthy report; UNKNOWN means the report could not be read, not that the system is healthy. These checks cover whether jobs ran and saved rows, not whether the market data behind them is correct.

    How to read these comparisons

    • Every figure is computed on resolved predictions only; each chart prints its own n.
    • Variants started at different times and need different minimum histories, so they are not measured on the same sample or period.
    • A higher accuracy bar is not a statistically conclusive ranking. Only the selection gate (Selected Model) applies a significance bar, and falling back to Original k-NN is the normal outcome when nothing clears it.
    Terms
    • Flat: Challenger's unadjusted read; on anomaly days it uses trend persistence, otherwise k-NN p_up.
    • Tilted: the flat read additionally nudged by a fresh mapped Foufi driver on anomaly days.
    • Regime anomaly: the backend's tripwire for days whose setup is unusual versus history — the conditions in which the k-NN has been empirically weakest; on those days Challenger switches to trend-persistence mode.
    • Trend-persistence mode: a simple trend continuation read used on anomaly days.
    • Calibrated model: a probability adjustment built from that model's own resolved history using decile bucket recalibration, rebuilt daily.
    • Local edge: How often a variant was right, above a 50% coin flip, at historical moments that looked like today when it made the same directional call (shown as the LCA / selection score).
    • Significance threshold: The bar a variant's local edge must clear before it is selected; it gets stricter the more variants are compared (shown as Corrected Threshold). If nothing clears it, the system falls back to Original k-NN.

    Selected Model —

    The "council build" — Condition-Matched Selection. Not "which variant has the best recent accuracy" (that's the shallow, explicitly-rejected approach this session already identified as noise-chasing) — instead, "among historical moments that looked like THIS one, which variant was actually right when it made THIS SAME directional call." A variant needs 50+ resolved predictions of its own before being considered, and its local edge must clear a significance bar that gets stricter the more variants are being compared. If nothing clears the bar, it explicitly falls back to Original k-NN rather than forcing a confident-looking pick — that fallback is the common, healthy state early on, not an error.

    Model Health & Recent Trend — is it actually improving?

    "Recent" is the last 40 resolved predictions for each combo; "Prior" is everything before that — computed by differencing the same expanding-window data the charts above already use, not a separate fetch. This exists specifically to answer "did that last fix actually help" without needing to remember what the numbers were last time or query the database by hand. Recent sample sizes here are still small (30-50) — a single-digit swing is normal noise, not a verdict.

    The indented "↳ Calibrated" rows are a genuinely different thing from the row above them, not a duplicate: they're a probability adjustment built from that model's OWN accumulated resolved history (decile-bucket recalibration, rebuilt daily), reused as-is for both the core model and Challenger. Never replaces the row above it — shown separately so whether this adaptive layer actually helps gets decided by watching it over real time, not assumed on the way in. Needs its own 20+ resolved predictions before the underlying curve exists at all, on top of the 50 this table already requires — will show "not enough history" for longer than the row above it, that's expected.

    Combined Accuracy — which formula?

    Simple average treats all 4 coin/horizon combos equally regardless of how many resolved predictions back each one. Pooled (n-weighted) is mathematically the same as Σcorrect/Σresolved — a combo with 150 resolved predictions gets proportionally more say than one with 20. They're the only two meaningfully different formulas; a third "weighted by n" option would just be pooled again.
